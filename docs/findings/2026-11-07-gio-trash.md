# Finding: `gio trash` for the finder's Delete

**Date:** 2026-11-07 · **Plan:** [finder menu](../plans/2026-11-07-finder-menu.md)

## Question

The finder's right-click menu gets a **Delete**. Should it move files to the trash with `gio trash` or delete
them with our own code? And what happens where there's no trash? The plan has to choose between:

- `gio trash`,
- the freedesktop trash spec written ourselves, or
- the `trash` crate (a new dependency, so the user would have to run `cargo fetch`).

Two smaller questions:

- Does the client already get right-clicks and pointer moves (for highlighting the item under the pointer)?
- Can a rename refuse to overwrite without a race?

## Method

Machine: Ubuntu 24.04-based, Linux 6.8.0-147 x86_64, GLib `gio version` 2.80.0. `/home` is its own ext4
partition. `/` (and so `/tmp`) is another ext4 partition.

```sh
mkdir -p ~/.cache/tb-trash-test/dir/sub && echo hi > ~/.cache/tb-trash-test/a.txt && touch ~/.cache/tb-trash-test/dir/sub/x
/usr/bin/time -f "%e s" gio trash ~/.cache/tb-trash-test/a.txt; echo "exit $?"
/usr/bin/time -f "%e s" gio trash ~/.cache/tb-trash-test/dir;   echo "exit $?"
cat ~/.local/share/Trash/info/a.txt.trashinfo
echo hi > $SCRATCH/b.txt          # $SCRATCH is under /tmp, on /
/usr/bin/time -f "%e s" gio trash $SCRATCH/b.txt; echo "exit $?"
gio trash $SCRATCH/nope.txt; echo "exit $?"
```

The two test entries were then removed from `~/.local/share/Trash` by hand. Before removing each one, its
`.trashinfo` `Path=` line was checked.

Code checks:

- `grep -rn 1003h ~/.cargo/registry/src/*/crossterm-0.29.0/src/event.rs`
- `rustix-1.1.6/src/fs/at.rs`, where `renameat_with` is defined
- `grep 'cargo registry' Cargo.lock`: is `trash` a dependency already?


- **crossterm 0.29 `EnableMouseCapture`** (used by `client.rs`) turns on `?1000h ?1002h ?1003h ?1015h ?1006h`.
  `1003` is any-motion tracking, so pointer moves arrive as `MouseEventKind::Moved`, and right-clicks arrive as
  `Down(MouseButton::Right)`. `Server::mouse` already passes every event over a finder pane to
  `Finder::handle_mouse`, which ignores the right button today.
- **`rustix::fs::renameat_with`** with `RenameFlags::NOREPLACE` exists under
  `cfg(any(apple, linux_kernel, target_os = "redox"))`. rustix is already a dependency with the `fs` feature.
- The `trash` crate isn't in `Cargo.lock`.

## Conclusions

- **Use `gio trash`.** It takes 10 ms for a file and for a folder in the home partition, and it writes the
  standard `.trashinfo`, so the desktop's Trash can restore the files. That's fast enough to run in the server
  thread. It needs no new crate.
- **Where there's no trash, `gio` fails cleanly.** On `/` ("system internal mounts") it exits 1 with a
  one-line reason and leaves the file alone. The finder can show that reason and offer to delete for good after
  a `y`. It must never fall back to deleting silently.
- **If `gio` is missing** (a machine without GLib's tools), the finder treats it the same way: it can't trash,
  so it asks.
- **Renames can refuse to overwrite atomically** with `renameat2(RENAME_NOREPLACE)` through rustix. Plain
  `std::fs::rename` would silently replace an existing file.
- **Still unknown:**
  - Whether the user's terminals pass right-clicks to the program rather than opening their own menu. Most do
    while the program has mouse reporting on, and Shift+right-click usually gets the terminal's own menu
    (**estimate**, not checked per terminal).
  - Trashing on other mounts (USB drives, network shares) wasn't tried. `gio` uses `$topdir/.Trash-$uid` there
    when it can.
