# Release v0.3.0: upgrading from 0.2.0, `tos update`, rollback, and the update check

## Question

Does the [tos update plan](../plans/2026-11-10-tos-update.md) work against the real releases?

- Does the one-liner turn a 0.2.0 plain-file install into the versions layout?
- Does it add `~/.local/bin` to `PATH` when that's missing?
- Do `tos update` and `tos update --version` behave as expected?
- Does a 0.3.0 server's update check reach GitHub?

This closes the plan's "Release" step, and it tests upgrades between releases, which the
[v0.2.0 finding](2026-11-10-release-v0.2.0.md) left open.

## Method

On 2026-11-10. Tag `v0.3.0` on `692ffef`, pushed by the user, built by release run `42782944407` (all jobs
succeeded). A clean `ubuntu:22.04` container, with a new user `t` (`useradd -m -s /bin/bash t`) whose `PATH`
doesn't include `~/.local/bin`. It ran:

```sh
R=https://github.com/hugegene/termos/releases
curl -fsSL $R/download/v0.2.0/install.sh | TOS_VERSION=0.2.0 sh     # 1. 0.2.0 with its own installer
~/.local/bin/tos attach -b work                                      #    and a session running 0.2.0
curl -fsSL $R/latest/download/install.sh | sh                       # 2. the one-liner (0.3.0)
bash -i -c 'tos --version'; ~/.local/bin/tos ls                      #    a new shell; the old session
~/.local/bin/tos update                                              # 3. already the newest
~/.local/bin/tos update --version 0.2.0; ~/.local/bin/tos update     # 4. back to 0.2.0, then update again
curl -fsSL $R/latest/download/install.sh | sh                       # 5. forward with the one-liner
tos kill work; tos attach -b fresh; sleep 3; cat ~/.local/state/termos/update-check   # 6. the check
```

After each step: whether `~/.local/bin/tos` is a symlink, and `ls ~/.local/share/termos/versions`.

## Conclusions

- **The one-liner upgrade works from a 0.2.0 install:** the plain file becomes the symlink into
  `versions/0.3.0`. The PATH line goes into `~/.bashrc` once, and a new shell finds `tos`. The 0.2.0
  session keeps running and is still listed by the 0.3.0 client: `PROTOCOL_VERSION` is 3 in both, so no
  `tos kill` was needed.
- **Rollback works and keeps the version it came from.** Rolling back to 0.2.0 left `0.2.0 0.3.0` in place.
- **The real update check works:** a 0.3.0 server asked GitHub, got 0.3.0, and recorded it. As expected,
  there was no notice, since nothing is newer.
- **Two rough edges in `tos update`** (not decided):
  - **When already the newest,** it downloads and reinstalls the same version. It could check `latest` first
    (the same one request as the notice) and say `tos 0.3.0 is already the newest`.
  - **`--version` older than 0.3.0** installs a `tos` without the `update` command, so only the one-liner
    can bring it forward. `tos update` could warn about that first, or refuse.
- **A loose hint:** the installer's "a tos server from before is still running" note looks for any process
  named `tos`. Here that was true (the 0.2.0 session), but it would also show when the running server is
  already the new version.
- **Still unknown:**
  - The status bar notice with a real newer release. That needs a release after 0.3.0; the e2e test covers it
    with a stand-in server.
  - The upgrade on macOS by hand.
